## 一、背景与结论固化

### 1.1 原始需求

1. **固定主流程 + 子流程**（node-red subflow 心智）：主流程固定为「通道接入（MQTT / Modbus TCP / BACnet 等）→ 输出统一为 string / json / bytes 三类报文 → 各子流程解析出设备与测点 → 聚合为一个大 JSON → MQTT 发布或落库」；
2. **充分解耦**：子流程由开发标准化开发；交付只配置采集拿到 string/json/bytes 报文；平台端只消费最终大 JSON；
3. **Excel 点表批量导入**：导入通道设备配置、子流程、测点清单即完成采集上数（导入即生效），交付提速。

### 1.2 评估结论（融合路线，已裁定）

| 维度 | 裁定 |
| ---- | ---- |
| 引擎 | RuleGo v0.37.2（已 subtree 内嵌 + bridge 桥接，见 02 文档实施状态） |
| 业务模型 | **ThingsGateway 式三级模型**（通道 Channel / 设备 Device / 测点 Variable），作为 GVA 业务库的**唯一事实源** |
| 执行产物 | 规则链 DSL 为**派生物**（可由三级模型随时重建），经 bridge REST 热部署到 RuleGo |
| 设备两类分支 | **寄存器型**（Modbus/BACnet 等结构化点表）→ `x/iotRead` 点位直采；**报文型**（传感器主动上报）→ `flow` 子规则链解析（对应需求 1 的"子流程"） |
| 通道协议覆盖 | MQTT（核心库）、Modbus TCP/RTU、BACnet/IP、S7、OPC UA、SNMP、FINS、MC、IEC104、DL/T645、EIP、串口、HJ212（components-iot，纯 Go 无 CGO） |
| 导入交互 | 借鉴 ThingsGateway：Excel 多 sheet + 名称外键 + 预览确认 + 新增/更新两集合 upsert |
| 心智边界 | 交付人员只见「通道/设备/测点」，**不见规则链**；子流程开发只见 DSL 与输入输出契约 |

### 1.3 设计原则

1. **事实源唯一**：GVA 业务库三级模型是配置事实源；rulego 侧（当前 filestore）只存派生 DSL，损坏可重编译恢复；
2. **配置态与运行态分离**（借鉴 ThingsGateway）：导入/编辑只动配置库；生效须经「编译 → 部署」显式动作（导入向导内含该动作，对用户透明）；
3. **主流程固定**：主链由模板实例化，交付侧无法破坏「类型归一 → 子流程/直采 → 聚合 → 输出」的结构契约；
4. **类型归一契约**：进入解析分支的报文必须是 string / json / bytes 三类之一，由主链内置归一节点强制；
5. **fail-closed**：编译器遇未知 driver/数据类型/地址格式一律报错拒绝，不静默降级；
6. **平台侧收口**：所有链管理操作经 GVA 后端转发 bridge（服务端内部调用），前端不直接 CRUD `/rulego/**`（例外：RunLog 调试 WebSocket 直连）。

## 二、总体架构

### 2.1 架构总览

```
交付侧                    GVA 平台侧（事实源 + 管理）                 引擎侧（派生物 + 执行）
──────                    ──────────────────────────                 ──────────────────────
Excel 点表（3 sheet）──▶  ⑤ 导入向导 API（解析/校验/预览/upsert）
                          │
                          ▼
                          ① 三级模型（collect_channels/devices/variables）+ 设备类型/子流程库
                          │
                          │ ② 编译器（模板实例化：模型 → 规则链 DSL，纯函数）
                          ▼
                          ③ 部署联动（服务端内部调 bridge REST：save + operate/deploy）
                          │                                              │
                          │                                              ▼
                          │                    RuleGo 引擎：每通道一条主链 + 每设备类型一条子链
                          │                      endpoint/schedule 或 endpoint/mqtt（通道入口）
                          │                        ├─ 寄存器分支：x/iotRead（driver/points）
                          │                        └─ 报文分支：归一 → flow(子链解析)
                          │                      groupAction/join 聚合 → jsTransform 组装大 JSON
                          │                        ├─ dbClient → UPSERT collect_realtime（实时值）
                          │                        └─ mqttClient → 发布大 JSON（供第三方订阅）
                          ▼
⑦ 采集监控页 ◀──────────  ⑥ 实时数据查询 API + RunLog WS（前端直连 ?token=）
```

### 2.2 两条数据流

| 链路 | 路径 | 权限 |
| ---- | ---- | ---- |
| **管理链路**（配置/导入/编译/部署） | 前端 → GVA `/api/collect/**` → 服务端内部调用 `127.0.0.1:8888/rulego/api/v1/**` | GVA Casbin 常规 (path, method) 策略，API 管理正常录入 |
| **采集链路**（数据面） | 设备/传感器 → rulego 链 → 大 JSON → `dbClient` 落 `collect_realtime` + `mqttClient` 发布；监控页 → GVA 查询 API / RunLog WS | 引擎侧无用户面（链内节点直连数据源与库）；RunLog WS 走 GVA JWT（`?token=` query，rulego 原生支持） |

### 2.3 与现有集成的关系

- 复用 02 文档 M2/M3 已落地的：bridge 挂载（`/rulego/**`）、`mapXToken` 头映射、`gvaEnvelope` 信封、GVA JWT/Casbin 桥接（`server/plugin/rulego/`）；
- 新增依赖一项：胶水层按需引入 `rulego-components-iot`（空导入注册节点，M4.1 既有设计），建议只 import 用到的协议包：`external/modbus`、`external/bacnet`、`external/deviceio`（`x/iotRead`/`x/iotWrite` 所在）；
- 配置文件无需变更（`resource/rulego/config.conf` 已具备 `debug=true`、data_dir 收敛）。

## 三、领域模型与数据库设计

存储：GVA 业务库（PgSQL，与 gin_vue_admin 同库），表前缀 `collect_`，均含 `global.GVA_MODEL`（ID/CreatedAt/UpdatedAt/DeletedAt 软删）。

### 3.1 实体关系

```
collect_channels 1 ──▶ N collect_devices 1 ──▶ N collect_variables
        │                      │
        │                      └──▶ N:1 collect_device_types 1 ──▶ 1 collect_parse_chains（报文型）
        └──▶ N collect_deployments（每通道的编译部署历史，含当前生效版本）
collect_realtime（测点最新值，由采集链 UPSERT，按 point_key 定位）
```

### 3.2 表结构

**collect_channels（通道）**——对应 ThingsGateway.Channel：一条物理/逻辑连接 + 驱动。

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| name | varchar(64) 唯一 | 通道名称（Excel 名称外键锚点） |
| access_mode | varchar(16) | `poll`（轮询采集：Modbus/BACnet/S7…）或 `report`（主动上报：MQTT 订阅） |
| driver | varchar(32) | 驱动标识：`modbus` / `bacnet` / `s7` / `opcua` / `snmp` / `fins` / `mc` / `iec104` / `dlt645` / `eip` / `mqtt` |
| conn_config | jsonb | 连接参数（结构随 driver，字段与 components-iot 配置元数据对齐：`server`、`tcpConfig`、`rtuConfig`、MQTT 的 broker/topic/qos 等） |
| poll_interval | int | 通道默认轮询周期 ms（设备级可覆盖） |
| output_config | jsonb | 大 JSON 输出配置：`mqttPublish{topic,qos}`、`dbWrite{enable}`，缺省都开 |
| enable | bool | 通道使能（false → 编译时跳过 + 已部署链下线） |
| remark | varchar(255) | 备注 |

**collect_devices（设备）**——对应 ThingsGateway.Device：通道下的采集单元。

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| channel_id | uint FK | 所属通道 |
| name | varchar(64) | 设备名称（**通道内**唯一，Excel 外键锚点） |
| device_kind | varchar(16) | `register`（寄存器型，走 x/iotRead）/ `report`（报文型，走子流程） |
| device_type_id | uint FK 可空 | 报文型必填 → collect_device_types |
| unit_id | int 可空 | 寄存器型站号（Modbus unitId 等） |
| poll_interval | int 可空 | 设备级周期覆盖（ms） |
| props | jsonb | 驱动扩展属性（随 driver 元数据校验） |
| enable | bool | 设备使能（false → 编译时剔除该分支） |
| remark | varchar(255) | |

**collect_variables（测点）**——对应 ThingsGateway.Variable。

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| device_id | uint FK | 所属设备 |
| name | varchar(64) | 测点名（**设备内**唯一，大 JSON 的 point.name） |
| addr | varchar(64) | 寄存器型：协议地址格式（Modicon `40001`、BACnet `ai:1`、S7 `DB1.DBD0`）；报文型：报文内取数路径（如 JSONPath，供子流程契约引用） |
| data_type | varchar(16) | `INT16/UINT16/INT32/UINT32/FLOAT32/FLOAT64/BOOL/STRING/BYTE[]` |
| scale / offset | decimal | 线性换算 `value*scale+offset`（编译进 points 字段） |
| endian | varchar(8) 可空 | `ABCD/CDAB/BADC/DCBA`（Modbus/FINS） |
| collect_group | varchar(32) | 采集分组（同组同批读取，编译时合批依据） |
| read_expr | varchar(255) 可空 | 复杂读表达式（线性换算不够时；一期仅存储与透传给子流程，不做链上翻译） |
| rw | varchar(8) | `R` / `RW`（一期只读采集，RW 仅透传） |
| unit | varchar(16) | 工程单位 |
| enable | bool | |
| remark | varchar(255) | |

**collect_device_types（设备类型，报文型）**

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| name | varchar(64) 唯一 | 设备类型名（如 `XX厂商温度传感器JSON`） |
| payload_type | varchar(8) | `string` / `json` / `bytes`（输入契约） |
| parse_chain_id | uint FK | 绑定的子流程链 |
| enable | bool | |

**collect_parse_chains（子流程库）**——开发标准化交付的解析链。

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| name | varchar(64) 唯一 | 子链名 |
| version | int | 语义版本（发布后递增） |
| dsl | text | 规则链 DSL（输入契约：string/json/bytes 报文 → 输出契约：测点键值数组 JSON） |
| input_contract | varchar(255) | 输入契约说明（人读） |
| test_payload | text | 测试报文样例（导入前回放验证用） |
| status | varchar(16) | `draft` / `published`（仅 published 可被设备类型引用） |

**collect_deployments（部署记录）**

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| channel_id | uint FK | 通道 |
| chain_id | varchar(64) | rulego 链 ID（`collect_ch_<channelId>`） |
| dsl_hash | varchar(64) | 编译产物 SHA-256（**幂等依据**：与已部署哈希相同则跳过重部署） |
| dsl_snapshot | text | 编译快照（审计/回滚参照） |
| template_version | varchar(16) | 编译模板版本 |
| status | varchar(16) | `deployed` / `rolled_back` |
| operator_id | uint | 操作人（导入向导触发时为导入人） |

**collect_realtime（测点最新值）**——采集状态查看的数据底座。

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| point_key | varchar(128) PK | `<channelId>:<deviceId>:<variableName>` |
| channel_id / device_id | uint | 冗余定位列（带索引，监控页过滤） |
| value | text | 最新值（字符串化） |
| quality | varchar(16) | `good` / `bad`（解析错误）/ `timeout`（窗口内未返回） |
| error_msg | varchar(255) | quality=bad 时的错误信息 |
| ts | timestamptz | 采集时间戳 |

> 历史数据存储（时序库）、变量级报警/滤波为非目标（见十二），一期实时表只保留最新值，UPSERT 语义。

## 四、编译器设计（三级模型 → RuleGo DSL）

### 4.1 编译单元与产物

| 项 | 规则 |
| ---- | ---- |
| 编译单元 | 一个通道（含其下全部使能设备/测点） |
| 主链产物 | 每通道一条：chain ID = `collect_ch_<channelId>`，name = `采集主链-<通道名>` |
| 子链产物 | 每设备类型一条：chain ID = `collect_pc_<parseChainId>`，由子流程库独立发布部署（不随通道编译重复生成，主链经 `flow` 节点 `targetId` 引用） |
| 纯函数 | `Compile(channel, devices, variables, deviceTypes, parseChains, tpl) (dsl []byte, hash string, err error)`——无 IO，单测覆盖核心 |
| 模板版本 | `template_version` 随模板演进递增；提供「全量重编译」管理命令用于模板升级后的批量刷新 |

### 4.2 主链固定模板（寄存器型通道，DSL 范式）

节点 type 均为 v0.37.2 实测注册名。结构固定为四段：**入口 → 采集分支 → 聚合 → 输出**。

```json
{
  "ruleChain": {"id": "collect_ch_1", "name": "采集主链-1号配电室Modbus", "root": true, "additionalInfo": {"templateVersion": "1", "kind": "collect-main"}},
  "metadata": {
    "nodes": [
      {"id": "n_trigger", "type": "endpoint/schedule", "name": "通道轮询触发",
       "configuration": {"interval": 5000, "cron": ""}},

      {"id": "n_dev_1", "type": "x/iotRead", "name": "设备-1号电表",
       "configuration": {"driver": "modbus", "server": "tcp://192.168.1.100:502", "unitId": 1,
         "points": [
           {"name": "电压", "addr": "40001", "type": "FLOAT32", "scale": 0.1},
           {"name": "电流", "addr": "40003", "type": "FLOAT32", "scale": 0.001},
           {"name": "功率", "addr": "40005", "type": "FLOAT32", "endian": "CDAB"}
         ]}},

      {"id": "n_dev_2", "type": "x/iotRead", "name": "设备-2号电表",
       "configuration": {"driver": "modbus", "server": "tcp://192.168.1.100:502", "unitId": 2,
         "points": [/* 同上，来自 collect_variables */]}},

      {"id": "n_agg", "type": "groupAction", "name": "设备分支聚合",
       "configuration": {/* 等待全部设备分支返回或窗口超时 */}},

      {"id": "n_build", "type": "jsTransform", "name": "组装大JSON",
       "configuration": {"jsScript": "/* 模板内置固定脚本：见 4.4 契约 */"}},

      {"id": "n_db", "type": "dbClient", "name": "实时值落库",
       "configuration": {"driverName": "postgres", "dsn": "${global.gvaDsn}", "sql": "UPSERT collect_realtime ... ON CONFLICT (point_key)", "params": [".values"]}},

      {"id": "n_mqtt", "type": "mqttClient", "name": "大JSON发布",
       "configuration": {"server": "tcp://127.0.0.1:1883", "topic": "gva/collect/${metadata.channelId}", "qos": 1}}
    ],
    "edges": [
      {"fromId": "n_trigger", "toId": "n_dev_1", "relation": "Success"},
      {"fromId": "n_trigger", "toId": "n_dev_2", "relation": "Success"},
      {"fromId": "n_dev_1",   "toId": "n_agg", "relation": "Success"},
      {"fromId": "n_dev_2",   "toId": "n_agg", "relation": "Success"},
      {"fromId": "n_agg",  "toId": "n_build", "relation": "Success"},
      {"fromId": "n_build","toId": "n_db",   "relation": "Success"},
      {"fromId": "n_build","toId": "n_mqtt", "relation": "Success"}
    ]
  }
}
```

### 4.3 报文型分支差异（access_mode=report）

| 环节 | 寄存器型（poll） | 报文型（report） |
| ---- | ---------------- | ---------------- |
| 入口节点 | `endpoint/schedule`（interval = 通道/设备周期） | `endpoint/mqtt`（订阅通道配置的 broker/topic；设备识别：报文 metadata 或 topic 通配映射 → device_key） |
| 采集分支 | `x/iotRead`（每设备一节点，含 points） | **类型归一节点（jsTransform，模板内置）→ `flow` 子链节点**：`{"targetId": "collect_pc_<parseChainId>", "extend": false}` |
| 归一契约 | 不需要（x/iotRead 输出即结构化 points） | 强制 string/json/bytes 三选一：非约定类型直接转 bad 质量（进入大 JSON 的 error 字段，不中断链） |
| 测点来源 | points 数组（三级模型直译） | 子链输出测点数组；`collect_variables.addr` 存报文内取数路径作为契约对照 |

两类分支可在**同一通道共存**（如 Modbus 采集 + MQTT 上报混合），编译器按设备 `device_kind` 分别生成分支，共用聚合与输出段。

### 4.4 大 JSON 契约（主链与平台端的唯一界面）

```json
{
  "channel": {"id": 1, "name": "1号配电室Modbus", "ts": "2026-09-08T15:00:00+08:00"},
  "devices": [
    {"device": "1号电表", "deviceKey": "1", "ts": 1757316000123,
     "points": [
       {"name": "电压", "value": 220.1, "quality": "good", "ts": 1757316000123},
       {"name": "电流", "value": null,  "quality": "timeout", "error": "window expired"}
     ]}
  ]
}
```

- 组装脚本是**模板内置的固定 jsTransform**（`n_build`），交付侧不可改——这是"平台端只解析大 JSON"解耦承诺的技术保证；
- `quality` 三态：`good` / `bad`（设备返回 error 或子链解析失败）/ `timeout`（聚合窗口内未返回）——部分设备失败**不阻塞**整体输出，平台端按 quality 决定展示与告警。

### 4.5 翻译规则（三级模型 → DSL 位置）

| 模型字段 | DSL 位置 |
| -------- | -------- |
| channel.driver / conn_config | 各 `x/iotRead` 的 `driver` / `server`·`tcpConfig`·`rtuConfig`；或 `endpoint/mqtt` 的 broker 配置 |
| channel.poll_interval | `endpoint/schedule` 的 interval（**分组**：按设备周期取 LCM 生成 1~N 个 schedule 分支，见风险 3） |
| device.unit_id | `x/iotRead` 的 `unitId` |
| device.enable=false | 该分支节点与边不生成 |
| variable.addr/type/scale/offset/endian/name | points 数组元素直译（`type` 大写枚举、Modicon 地址原样） |
| variable.collect_group | 同设备内同组合并为同一 points 数组批次（相邻地址合批由 x/iotRead 内部自动优化，无需编译器排序） |
| device_type.payload_type | 归一节点的目标类型 |
| device_type.parse_chain_id | `flow` 节点 `targetId` |

### 4.6 部署联动

```
编译（模型→DSL+hash）
  ├─ hash == 当前 deployed 记录 → 幂等跳过（导入未变更通道不产生任何引擎动作）
  ├─ POST /rulego/api/v1/rules/collect_ch_<id>   （save，服务端内部 HTTP + 服务账号 GVA JWT）
  ├─ POST /rulego/api/v1/rules/collect_ch_<id>/operate/deploy   （热部署，立即生效）
  └─ 写 collect_deployments（dsl_snapshot/hash/template_version）
通道禁用/删除 → operate/undeploy 下线 → 记录 rolled_back
```

- 服务端内部调用 bridge 用**服务账号 JWT**（GVA 888 角色，短时效，服务启动时签发缓存），复用既有认证桥接，不新开旁路；
- 子流程链发布独立于通道编译：`collect_parse_chains.status=published` 时经同一部署通道发布 `collect_pc_<id>`；被引用链不存在时编译器报错（fail-closed）。

## 五、Excel 点表导入设计（后端）

### 5.1 模板（一个工作簿、三个 sheet，GVA 后端生成模板下载）

| sheet | 列（顺序即模板顺序） | 校验 |
| ----- | -------------------- | ---- |
| 通道 | 通道名称*、接入方式*（poll/report）、驱动*（modbus/bacnet/…）、连接配置JSON*、轮询周期ms、MQTT发布topic、使能、备注 | 驱动枚举；连接配置按 driver 的**组件配置元数据**校验（必填/格式，元数据取自 components-iot 的 `label/required/desc` tag，服务端启动时反射生成校验规则，同一份元数据同时用于生成模板表头批注） |
| 设备 | 所属通道名称*（外键）、设备名称*、设备类型*（register/report）、设备类型名（report 必填，须已存在且 published）、站号、采集周期ms、扩展属性JSON、使能、备注 | 名称外键在**库内已有 + 本文件通道 sheet** 联合域解析；通道内重名拒绝 |
| 测点 | 所属设备名称*（外键，格式 `通道名称/设备名称`）、测点名称*、地址*、数据类型*、系数、偏移、字节序、采集分组、读写、单位、使能、备注 | 地址格式按 driver 正则（Modicon `4[0-9]{4}` 等）；数据类型枚举；设备内重名拒绝 |

\* 必填。名称外键沿用 ThingsGateway 的"按名称解析"交互——实施人员按名字写，导入时解析成 ID，导出时反向带出名称。

### 5.2 导入流程（导入即上数）

```
① 上传 xlsx（≤10MB）
② excelize 流式解析三 sheet（依赖已有）
③ 逐行校验 → 生成三分类结果：insert[]（新增）/ update[]（按业务键匹配已有记录）/ error[]（行号+原因）
④ 返回预览（三分类统计 + 错误行明细 + 每 sheet 前 N 行diff 展示数据）
⑤ 用户确认（可选勾选「自动编译部署变更通道」，默认开）
⑥ 事务：upsert 通道/设备/测点（gorm 批量，按 sheet 依赖顺序）
⑦ 对发生变更的通道逐个执行 4.6 部署联动（幂等）
⑧ 返回部署结果汇总（成功通道数 / 失败原因 / 跳过（无变更）数）
```

### 5.3 错误与部分导入策略

- 行级错误不阻塞其他行（错误行进 error[] 报告，模板可下载含错误标注的回执文件）；
- sheet 级致命错误（如设备 sheet 的通道外键全部无法解析）→ 该 sheet 整体不入库，前置 sheet 已入库的保留并提示；
- 部署阶段单通道失败不影响其他通道，失败通道在部署结果中给出编译器错误（fail-closed 信息直接透出）；
- 全程操作日志走 GVA 操作记录（operator 日志），导入行为可审计。

### 5.4 导出

三级模型 → 同结构 Excel 导出（`通道/设备/测点` 三 sheet，外键列输出名称），支撑"导出→修改→再导入"的交付闭环与配置备份。

## 八、采集状态与实时数据链路

### 8.1 大 JSON 消费路径（推荐主路径）

主链 `dbClient` 节点**直写** `collect_realtime`（PgSQL `INSERT ... ON CONFLICT (point_key) DO UPDATE`）——不经 MQTT 回环，少一跳、事务性强；`mqttClient` 并行发布仍保留（第三方订阅与边缘级联用，`output_config` 可关）。

- dbClient 的 dsn 经 `${global.gvaDsn}` 注入（rulego `[global]` 自定义配置段），账号用 GVA 库的**只写受限账号**（仅 collect_realtime 的 UPSERT 权限），与 GVA 主连接隔离；
- 大 JSON → collect_realtime 的行展开由固定 SQL+params 完成（模板内置，随 `n_build` 的输出结构共同演进，模板版本化）。

### 8.2 实时表与查询

- 监控页轮询 `GET /api/collect/realtime`（带通道/设备/质量过滤 + 分页）；数据量 = 全部测点数（万级内无压力，`(channel_id, device_id)` 索引）；
- 超过轮询承载（>5 万测点）时二期演进：值推送（WS 订阅 MQTT 回环）或时序库直查——一期不做。

### 8.3 通道/设备运行状态判定（无侵入推导）

| 对象 | 状态 | 判定来源 |
| ---- | ---- | -------- |
| 通道 | 已部署/未部署/部署失败 | collect_deployments 最新记录 |
| 通道 | 运行中/已停止 | 部署状态 × channel.enable |
| 设备 | 在线/异常/离线 | 数据新鲜度：collect_realtime 该设备全部测点 ts 距今 > 3×采集周期 → 离线；存在 bad → 异常；否则在线 |
| 测点 | good/bad/timeout | quality 字段直读 |

> 该方案不依赖引擎内部状态 API（v0.37.2 无设备级状态端点），用数据新鲜度推导，实现简单且与引擎解耦；RunLog 提供微观诊断补充。

## 九、关键技术决策与风险

| # | 风险/决策 | 等级 | 对策 |
| - | --------- | :--: | ---- |
| 1 | **连接复用**：每设备一个 x/iotRead 节点 = 各建一条连接；ThingsGateway 是通道级共享连接 | 中 | PoC 实测量级（单通道 ≤30 设备 TCP 连接通常可接受）；超限场景编译器提供「同 server 多站号合并为单节点多批」编译选项（x/iotRead 支持运行期换 unitId 的能力 PoC 验证）；结论回填本文档 |
| 2 | **聚合窗口语义**：groupAction 等待语义与超时行为需实测 | 高 | PoC 首项验证内容：慢设备/离线设备是否阻塞窗口；不满足则在 n_build 前置固定超时网关节点（jsTransform 计时兜底），模板版本化修正 |
| 3 | **变量级周期**：rulego 轮询是节点/endpoint 级 | 中 | 编译时按 poll_interval 分组：同周期设备归入同一 schedule 分支；不同周期生成多个 schedule 入口（LCM 对齐）；变量级周期一期收敛为"设备级+采集分组"粒度（文档明示交付约束） |
| 4 | **编译器正确性**：DSL 是手拼 JSON，结构错误运行期才暴露 | 中 | 编译产物先经 `POST /rulego/api/v1/rules/:id`（保存时引擎校验 DSL）再部署；编译器单测（模型→DSL 快照比对）+ 部署失败的回滚记录 |
| 5 | **filestore 规模**：链数量 = 通道数（百级内 OK） | 低 | 超出时启用 StoreProvider 落 PG（01 文档 M4.5 既有可选项），编译器无感 |
| 6 | **components-iot 引入增量** | 低 | 只 import 所用协议包（modbus/bacnet/deviceio + mqtt 走核心），不整库引入 |
| 7 | **高级组件不确定项**：`x/streamAggregator`、`x/tsdbWrite`（README 引用）注册名/能力未实测 | 低 | 一期不依赖；二期时序历史需求时 PoC 验证后纳入 |
| 8 | **dbClient 写库凭证**：链内直写业务库 | 中 | 受限 DB 账号（仅 collect_realtime UPSERT）；SQL 固定在模板内不由用户输入（防注入面收敛在编译器） |
| 9 | **导入事务边界**：三 sheet 依赖顺序 + 部署非事务 | 中 | 入库事务性保证；部署幂等（dsl_hash）+ 失败通道独立重试；文档明示"导入成功但部署失败"的可见性与补救路径（部署结果卡 + 单通道重部署） |

## 十三、P0 实测结论与实施偏差回填（2026-09-08，开发完成后固化）

以下结论均以 `server/plugin/rulego/poc_test.go` 与编译器单测固化为回归锚点，与正文冲突处以本节为准。

### 13.1 触发面架构修正（§4.2/§4.3 修正）

**实测**：RuleGo 链节点注册表（rulego.Registry）**没有**周期触发组件——`endpoint/schedule` 只注册在端点注册表（endpoint.Registry），链内以 `"schedule"` 或 `"endpoint/schedule"` 声明节点均报 `component not found`（回归锚点：`TestScheduleNotAvailableInChain`）。

**修正**：触发面收敛在 GVA 侧（`plugin/collect/service/trigger.go`）：

- **poll 通道**：GVA 内 cron（robfig，秒级）按通道周期调 `POST /rulego/api/v1/rules/:id/notify/JSON` 驱动链（异步、fire-and-forget）；
- **report 通道**：GVA 内 paho MQTT 订阅者（按通道 conn_config 的 server/topic）收报文 → notify（payload 首字符 `{`/`[` 判 JSON，否则 STRING）；
- 主链 root 固定为分发节点 `n_split`（jsTransform 直通），不再是 schedule/mqtt 端点节点；
- 通道部署/下线/删除联动增删触发器；GVA 重启时扫描 enable 通道全量恢复。

收益：rulego 侧无需管理 endpoint DSL 生命周期（引擎无该管理面），触发频率/启停/恢复全部在业务库可查可控。

### 13.2 join 聚合实测形态（§4.4 补充）

- join（mergeToMap=false）输出为 **JSON 数组**，元素为 WrapperMsg：`{nodeId, err, msg:{data(分支输出 JSON 字符串), metadata, ts}}`——组装节点必须 `JSON.parse(w.msg.data)`，`w.err` 即分支级错误（quality=timeout 判定来源）；
- join 超时（可配，模板取 max(10s, min(60s, 3×通道周期))）走 **Failure** 关系 → 模板内置降级节点输出空 devices 大 JSON（契约不中断）；
- x/iotRead **连接级失败走 Failure**（execute 同步端点表现为 400 GetError）——每设备分支必须配 `Failure → 兜底节点` 边，兜底输出该设备 timeout 片段回 join。

### 13.3 DSL 格式实测

- 边字段为 `metadata.connections[]`：`{fromId, toId, type}`（**不是** edges/relation）；
- 链内节点 type 直接用组件注册名（`x/iotRead`、`join`、`jsTransform`、`dbClient`、`mqttClient`、`flow`）；
- execute 同步端点响应会被 gvaEnvelope 包装为 `{code,data,msg}`，大 JSON 在 `data`。

### 13.4 组件引入修正（§风险 #6）

`x/iotRead`/`x/iotWrite` 所在包 `external/deviceio` 的 all.go **同包静态导入全部 10 个协议驱动**——同包文件无法按协议裁剪，单包引入即全量注册（均为纯 Go、无 CGO）。实施：`plugin/rulego/components.go` 空导入 deviceio 一个包。
