# 01 - RuleGo 服务端源码集成方案分析

> 分析视角：Go 高级后端工程师 / Go 高级架构师 / Git 高级仓库管理专家
> 日期：2026-09-05

## 一、背景与目标

gin-vue-admin（下称 GVA）需要引入 RuleGo 规则引擎能力（规则链、IoT/工作流/智能体编排），且要求**以源码方式**集成 RuleGo 服务端到本仓库，集成源为**开源提供方（官方）仓库的最新发布版本**，而不是仅作为远程 Go 依赖引用。目标：

1. 规则引擎能力随本仓库一同构建、发布，不依赖外部独立部署的 rulego-server 进程；
2. 保留跟随官方上游演进的能力，升级路径清晰、可控；
3. 与 GVA 既有体系（Gin 路由、JWT + Casbin 权限、插件机制、配置、Docker 部署）有机融合，不破坏 GVA 架构；
4. **webui-vben 前端明确舍弃**，规则链可视化管理由 GVA 前端自建。

## 二、集成对象盘点（基于官方 v0.37.2 浅克隆实测）

### 2.1 官方仓库与版本

- 官方仓库：https://gitee.com/rulego/rulego （与 GitHub 同名仓库互为镜像）；
- 最新 release：**v0.37.2**（已浅克隆验证）；
- 官方仓库为"核心库 + server/"**单仓双模块**结构，集成不需要任何第三方 fork 参与集成链路；
- git 跟踪文件 503 个，git pack 约 5 MiB——非常适合 subtree 入库；
- 许可证：Apache License 2.0（仓库根 LICENSE，整仓适用）。

### 2.2 两个 Go module

| 模块 | 位置 | go 版本 | 说明 |
| ---- | ---- | ------- | ---- |
| `github.com/rulego/rulego` | 仓库根 | 1.20 | RuleGo 核心库：engine（规则链引擎）、endpoint（rest/mqtt/websocket/net/schedule 端点）、components（action/filter/flow/transform/external 节点组件）、builtin（aspect/funcs/processor） |
| `github.com/rulego/rulego/server` | `server/` 子目录（独立 go.mod） | **1.25.0** | **RuleGo Server 服务端**：应用开发脚手架，App 生命周期 + 服务容器 + 模块化（rule/user/node/mcp/marketplace 等模块）+ 存储层 + 认证层 + Bridge 桥接层 |

### 2.3 rulego-server 的关键依赖（server/go.mod @ v0.37.2）

- `github.com/rulego/rulego v0.37.0`（核心库，**正式 tag 版本**）；
- 六大组件生态（独立模块，保持网络依赖）：`rulego-components` / `-components-ai` / `-components-ci` / `-components-discovery` / `-components-etl` / `-components-iot`；
- 其他重量级直接依赖：`cloudwego/eino`（LLM 应用框架）、`mark3labs/mcp-go`（MCP）、`golang-jwt/v5`、`bbolt`、`ini.v1`、`lumberjack`；
- go.mod 内的 replace 指令全部处于注释状态，即默认完全走网络模块解析——这对 subtree + replace 方案非常友好。

### 2.4 官方预设的宿主嵌入能力（bridge 包文档原文要点）

`server/bridge/handler.go` 包注释明确了嵌入模式三原则，这是本方案的架构基石：

1. **不监听端口**：`Bridge.Handler()` 返回标准 `http.Handler`，所有流量经宿主 HTTP 服务器（GVA 的 Gin，8888 端口）转发，宿主与 rulego-server **共用一个端口**；
2. **认证可托管**：`app.WithAuthenticator` / `app.WithAuthorizer` 注入宿主身份体系，配合 `bridge.WithoutLocalAuth()` 可**完全关闭** rulego 自带的登录/用户管理端点；
3. **响应可包装**：`bridge.WithResponseWrapper` 把 rulego 的裸 JSON 响应重组为宿主统一信封（GVA 的 `{code, data, msg}`），SSE/流式/二进制响应自动透传。

官方给出的 Gin 嵌入示例（bridge 包注释原文）：

```go
b, err := bridge.New(
    bridge.WithAppOptions(
        app.WithConfig(&cfg),                      // BasePath 设为 "/rulego"
        app.WithModules(bootstrap.DefaultModules()...),
        app.WithAuthenticator(&MyAuthenticator{}), // 宿主身份体系
        app.WithAuthorizer(&MyAuthorizer{}),
    ),
    bridge.WithoutLocalAuth(),                     // 关闭 rulego 自带 /login、/users*
    bridge.WithResponseWrapper(myEnvelope),        // {code,message,data} 信封
)
// 显式挂载到子路径（rulego 路由注册时已含 BasePath 前缀，勿 StripPrefix）
r.Any("/rulego/*path", gin.WrapH(b.Handler()))
```

### 2.5 GVA 侧现状（对接条件）

- 主模块 `github.com/flipped-aurora/gin-vue-admin/server`，go 1.24.0 / toolchain 1.24.2，Web 框架 Gin，端口 8888；
- **插件机制**：`server/plugin/<name>/plugin.go` 中 `init() { interfaces.Register(Plugin) }`，实现 `Register(group *gin.Engine)` 完成路由注册，`plugin/register.go` 空导入激活（announcement、auto、email、plugin-tool 即此形态）——rulego 胶水层可直接套用该形态；
- 认证体系：JWT（`x-token`）+ Casbin 角色授权；配置：Viper（`config.yaml`）；部署：Docker（golang:alpine 多阶段构建）+ docker-compose；
- 许可证：Apache 2.0（与 RuleGo 同源兼容）。

## 三、集成方式选型（Git 与 Go 工程视角）

候选方式共六种，逐一对比如下。评估维度：真源码入库、clone 即构建（无额外步骤）、上游同步能力、对 go.mod/CI 的影响、仓库体积、改造侵入性。

| 方式 | 源码入库 | clone 即构建 | 上游同步 | go.mod 影响 | 仓库体积 | 评价 |
| ---- | :--: | :--: | ---- | ---- | :--: | ---- |
| A. 纯 Go 依赖 `go get` | ❌（仅 go.sum） | ✅ | 跟官方 tag | 干净 | 0 | 不满足"源码方式"诉求，仅作基线 |
| B. **git submodule** 挂官方仓库 + replace 指向子模块路径 | ✅ | ❌ 需 `submodule update --init` | 指针式，快且显式 | replace 相对路径 | 不膨胀 | 可行但协作者/CI/IDE 摩擦大，易忘 init |
| C. **git subtree --squash** 整仓内嵌 `server/rulego/` + replace | ✅ | ✅ | `git subtree pull` 一条命令 | replace 两条 | +约 6~10MiB | **推荐**：兼顾"物理源码入库"与"可同步"，无 submodule 心智负担 |
| D. 源码快照拷贝（复制后不再跟踪上游） | ✅ | ✅ | ❌ 手工 diff | replace 两条 | 同 C | 最简单，但 RuleGo 组件生态周级发版，会失控漂移 |
| E. 拷贝并重写 module path 并入主 module | ✅ | ✅ | ❌ 路径重写污染 diff，几乎不可同步 | 无 replace，但 import 全改 | 同 C | 侵入最大，丢掉上游升级能力，**不推荐** |
| F. `go mod vendor` 全量 vendor | ✅（含全部传递依赖） | ✅（`-mod=vendor`） | 重新 vendor | vendor 目录 | **数百 MiB**（eino/阿里云 SDK/kafka 等） | 传递依赖爆炸，GVA 作为平台脚手架不宜，**不推荐** |

### 选型结论

**方式 C：git subtree（--squash）+ replace 双模块 + GVA 插件胶水层**，理由：

1. 以官方 v0.37.2 tag 为集成基线，"最新版本"有明确的、可复现的锚点；
2. "源码方式"落实得最完整：源码物理入库、clone 即构建、离线可编译，且保留 `git subtree pull` 跟随官方 release 的升级通道；
3. 官方仓库同时包含核心库与 server 两个 module，整仓 subtree 后用两条 replace 即可让主模块**零改动 import**（import 路径保持 `github.com/rulego/...` 不变）；
4. 六大 components 生态保持网络模块依赖（不入库），用版本化锁定——它们体量大、独立发版、非"服务端"本体，符合"集成 rulego 服务端"的诉求边界；
5. webui-vben 在官方仓库中本就未被 git 跟踪（本地构建产物），且已明确舍弃——subtree 天然不会引入，无需任何排除动作。

**备选**：若团队完全不能接受 subtree 工作流，退而选择 B（submodule）；若未来彻底接管 rulego 定制、放弃跟随上游，再演进为 D/E。

## 四、推荐方案的总体设计

### 4.1 目录规划

```
gin-vue-admin/
├── server/                              # GVA 后端主模块（github.com/flipped-aurora/gin-vue-admin/server）
│   ├── go.mod                           # 增：go 1.25.0、require 两条 rulego 模块、replace 指向树内路径
│   ├── plugin/
│   │   ├── register.go                  # 增空导入：_ ".../server/plugin/rulego"
│   │   └── rulego/                      # ★ 宿主胶水层（唯一允许依赖 rulego 的业务入口）
│   │       ├── plugin.go                #   GVA 插件形态：Register(group *gin.Engine) 挂载 bridge
│   │       ├── auth.go                  #   Authenticator/Authorizer → GVA JWT + Casbin 桥接
│   │       ├── wrapper.go               #   ResponseWrapper → GVA {code,data,msg} 信封
│   │       └── config.go                #   config.conf 定位与加载（可被 gva config 覆盖）
│   └── rulego/                          # ★ subtree 内嵌的 RuleGo 完整源码（上游只读，基线 v0.37.2）
│       ├── go.mod                       #   模块身份不变：github.com/rulego/rulego
│       ├── engine/ endpoint/ components/ builtin/ utils/ ...
│       └── server/                      #   模块身份不变：github.com/rulego/rulego/server
│           ├── bridge/ bootstrap/ app/ config/ services/ internal/ ...
│           └── cmd/server/              #   参考 main（GVA 不使用其 cmd，用 bootstrap + bridge 自行组装）
├── web/                                 # GVA 前端（规则链管理页面在此自建，webui-vben 已舍弃）
└── ...
```

原则：**树内源码（`server/rulego/`）视为第三方只读区，GVA 定制一律不落在树内**，全部通过 rulego-server 官方扩展点在胶水层实现：

| 定制诉求 | 官方扩展点 | 落点 |
| -------- | ---------- | ---- |
| 关闭自带登录/用户端点 | `bridge.WithoutLocalAuth()` | 胶水层 |
| 统一响应信封 | `bridge.WithResponseWrapper` | 胶水层 wrapper.go |
| JWT 认证/权限 | `app.WithAuthenticator` / `WithAuthorizer` | 胶水层 auth.go（桥接 GVA JWT + Casbin） |
| 规则链存储 | `store.StoreProvider`（默认 filestore） | 胶水层（M4 阶段可选替换） |
| 生命周期干预 | `app.WithHooks()`（5 个阶段） | 胶水层 |
| 组件裁剪 | `cmd/server/with_*.go` 的 build tag 模式 | 胶水层按需复制该模式，自建 tags |

### 4.2 go.mod 变更（GVA 主模块）

```go
module github.com/flipped-aurora/gin-vue-admin/server

go 1.25.0                    // 由 1.24.0 升级（rulego/server 要求 go 1.25.0）

require (
    github.com/rulego/rulego        v0.37.0  // 被 replace 到 ./rulego（官方 v0.37.2 内核版本）
    github.com/rulego/rulego/server v0.37.2  // 被 replace 到 ./rulego/server
    // 按需引入的组件生态（保持网络依赖，不源码化）：
    // github.com/rulego/rulego-components ...
)

replace github.com/rulego/rulego        => ./rulego
replace github.com/rulego/rulego/server => ./rulego/server
```

> 说明：replace 的相对路径相对主模块目录（`server/`）解析；树内模块与网络版本同 module path，`go mod tidy` 后 require 行仅是占位，实际编译取树内源码。

### 4.3 Go 版本与工具链影响（必须评估的连锁项）

| 影响点 | 现状 | 变更 |
| ------ | ---- | ---- |
| 主 go.mod | go 1.24.0 / toolchain 1.24.2 | go 1.25.0（本机 go 1.26.6 已满足） |
| `server/Dockerfile` | `golang:alpine`（跟随 latest，通常 ≥1.25） | 建议改为固定 `golang:1.25-alpine`，避免上游 go 指令继续抬升时静默失败 |
| CI（如有） | go-version 1.24 | 同步抬升至 1.25 |
| 其他子模块 | 无 | rulego 核心库 go 1.20 无额外约束 |

### 4.4 依赖树与构建产物影响

- `go.sum` 将显著增大（间接依赖引入 eino、mcp-go、WuKongIM、Kafka(Sarama)、阿里云 SDK 等；rulego-server 本身仅拉运行所需部分，组件包靠 build tag 控制编译范围）；
- 六大 components 生态**按需 require**：起步阶段建议只引 `rulego-components`（基础组件），AI/IoT/ETL 等 M2 之后再评估，避免一次性吞下整棵依赖树；
- 二进制体积与首次构建时间会上升；GOPROXY 建议沿用项目已配置的 `goproxy.cn,direct`。

### 4.5 运行时对接设计（GVA :8888 单端口）

```
浏览器/客户端
   │  http://<host>:8888/rulego/**          （GVA 前端亦可通过 /api 代理访问）
   ▼
Gin (GVA) ── JWT 中间件 → Casbin（可选路径级鉴权）
   │  r.Any("/rulego/*path", gin.WrapH(bridge.Handler()))
   ▼
Bridge（标准 http.Handler）── ResponseWrapper 统一信封
   ▼
App（rulego-server）── Module: rule / node / runlog / mcp / marketplace ...
   ▼
Store（默认 filestore：数据目录建议指向 gva 的持久化目录，如 server/resource/rulego/）
```

- **前端**：webui-vben **舍弃、不集成、不部署**。规则链可视化管理直接由 GVA 前端（Vue3 + Element Plus）自建页面承载（REST 走 `/rulego/**`），排期在 M4；M2/M3 阶段以 curl/API 调试验证功能闭环，不阻塞后端集成。
- **认证双轨消除**：rulego 自带 JWT 用户体系与 GVA 的体系重叠，M3 阶段用 `WithoutLocalAuth()` + `WithAuthenticator/WithAuthorizer` 桥接，rulego 侧不再产生独立登录态。
- **存储**：起步用默认文件存储（脚手架默认），数据目录纳入 GVA 的部署卷；后续可选实现 `store.StoreProvider` 落 GVA 的 PostgreSQL。

| # | 风险 | 等级 | 缓解 |
| - | ---- | :--: | ---- |
| 1 | go 1.24 → 1.25 升级波及 GVA 自身与 CI/Docker | 中 | 全量编译 + 现有测试回归；Dockerfile 固定 golang:1.25-alpine |

| 8 | 官方上游 go 指令继续抬升（如未来 go 1.26） | 低 | 升级前在分支上先行验证；Dockerfile/CI 版本随升级同步调整 |

## 七、方案对比的一票否决项复查

- E（路径重写内化）：GVA 是通用平台脚手架，RuleGo 组件生态活跃（周级发版），放弃同步能力不可接受 → 排除；
- F（vendor）：GVA 自身依赖已不少，再 vendor rulego 全树会让仓库膨胀失控 → 排除；
- B（submodule）：仅当团队 CI/开发流程对 submodule 有强支持时作为替代 → 备选。
