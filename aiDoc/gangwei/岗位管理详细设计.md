## 一、功能概述

### 1.1 功能定位

岗位（Post）是员工的**职务属性标签**，与部门（行政归属）、角色（权限）正交：

| 维度 | 承载语义 | 数量关系 | 本模块是否涉及 |
|---|---|---|---|
| 部门（sys_departments） | 行政归属，一人一主属部门 | 1 : N | 否（已有） |
| 角色（sys_authorities） | 权限/菜单可见性 | N : N | 否（已有） |
| **岗位（sys_posts）** | **职务标签，如"项目经理"** | **N : N（双向绑定）** | **是** |

JeeSite 中岗位是组织机构三要素之一（公司/部门/岗位），员工在员工表单中多选岗位，岗位侧可反向查看与调整所辖员工。本模块对齐该能力，并做如下简化：**不挂公司维度、不做岗位层级、不承载数据权限**（用户已明确：岗位管理独立、不涉及数据权限）。

**关键澄清——岗位是全局共享字典，不挂部门**：岗位表没有 `department_id`，"不同部门下的岗位不一样"这一约定**不存在**。「不同科室的护士长是不同的人」不需要岗位表表达，它由**员工实体承载组合信息**：员工 = （主属部门 `department_id`）∧（岗位 `sys_user_post`）。例如医院场景——「护士」「护士长」全院各只建一行，心内科/呼吸科的护士长都挂同一岗位行，部门归属由 `sys_users.department_id` 区分；不同院区的类似科室只是部门树的两个节点，岗位零重复维护。反观"岗位挂部门"方案：N 个科室重复建 N 行"护士"、命名漂移（护士/护师/护理员并存）、全院统计需跨行聚合。全局方案的唯一代价是字典里会有少量"仅单科室使用"的岗位行，无实际成本；唯一表达不了的是"某些岗位仅部分部门可选"，如未来有此诉求，走「适用部门」多选软约束扩展（见 §1.3-7），现阶段 YAGNI。

### 1.2 功能范围

**含**：

1. 岗位全栈 CRUD：分页列表（编码/名称关键字 + 岗位类型 + 状态筛选）、详情、创建、更新、删除（软删除）、停用/启用；
2. 岗位类型字典 `post_type`（随种子幂等注册，字典管理可自行维护选项）；
3. **岗位 → 员工**：「分配员工」弹窗（按部门树过滤 + 关键字搜索 + 分页勾选 + 已选回显），全量覆盖式绑定；
4. **员工 → 岗位**：用户管理编辑抽屉内嵌「岗位」多选，保存后绑定；
5. 岗位列表「关联员工数」列；员工删除时自动清理关联；
6. 菜单 / API / casbin / 字典幂等种子（Go 种子，范式同 `report_seed.go`）。

**不含**：

1. 数据权限（`sys_authority_data_scopes` 不扩展 scope_type，岗位不作为数据权限边界）；
2. 公司维度挂靠（`companyId`；JeeSite 有 corp_code，本期不做，字段层面预留见 §3.4）；
3. 岗位层级树（上级岗位）、岗位序列/职级体系；
4. 岗位与角色/菜单的任何联动（岗位不产生权限）；
5. 通用人员选择器组件（chooseUser/chooseDept，另立需求，见 §7 衔接说明）。

### 1.3 与 JeeSite 参考实现的差异裁定

| # | JeeSite | 本项目采用 | 裁定说明 |
|---|---|---|---|
| 1 | 关联表 `js_user_post` 以 `post_code` 关联 | 以 `post_id`（uint 主键）关联 | 本仓库全部系统关联均为 ID 关联（如 `sys_users.department_id`），编码仅作业务唯一标识，改码不断链 |
| 2 | `post_status` 沿用 JeeSite 字典语义（0 正常/2 停用/…） | `status int`：**1 启用 / 2 停用** | 对齐本仓库 system 域既有语义（`sys_departments.status`、`sys_users.enable`），前端 switch 直接复用 |
| 3 | 岗位挂公司（corp_code） | 不挂公司，岗位全局共用 | 用户裁定"岗位管理独立"；后续若需再增 `company_id` 列，关联语义不受影响 |
| 4 | 员工表单内直接多选岗位并随员工保存落库 | 用户抽屉内多选，**用户保存成功后独立调 `setUserPosts`** | 岗位模块独立持有全部关联 API，不侵入用户 create/update 现有接口签名；一致性风险见 §10 |
| 5 | 删除岗位物理删除并级联清理 | **有关联员工禁止删除**，无关联才可软删除 | 防误删丢痕迹；JeeSite 级联清理不可恢复，生产环境风险高 |
| 6 | `post_code` 唯一（全局） | 唯一索引 + Service 双重校验 | 与 `sys_departments.code` 同式（gorm `uniqueIndex`）；软删后编码不可复用的 trade-off 见 §10 |
| 7 | 岗位与公司/部门均无归属关系 | 明确**岗位全局共享、部门×岗位组合由员工承载**（§1.1 澄清）；如未来需"某些岗位仅部分部门可选"，预留**适用部门多选软约束**扩展（仅过滤下拉选项，非归属绑定） | 医院多科室共享"护士/护士长"等场景零重复维护；本期不做适用部门过滤 |

## 二、术语与业务规则

### 2.1 术语

| 术语 | 含义 |
|---|---|
| postCode | 岗位编码，业务唯一标识（如 `PM`、`HR`），全局唯一 |
| postName | 岗位名称（如"项目经理"），展示用 |
| postType | 岗位类型，字典 `post_type` 的 value（如高层岗位/中层岗位/基层岗位/普通岗位） |
| status | 状态：1 启用 / 2 停用；停用岗位不出现在员工侧可选下拉，已有关联保留 |
| sys_user_post | 员工-岗位关联表，N : N 双向绑定，复合主键 (user_id, post_id) |
| 全量覆盖式绑定 | 前端提交"当前最终态"集合，后端在事务内 diff：删除不在集合中的关联、插入新增的关联（与 `SetUserAuthorities` 多角色同式） |

### 2.2 核心业务规则

1. **编码唯一**：postCode 全局唯一（Service 查重，创建/更新均校验，更新排除自身）；
2. **删除保护**：`sys_user_post` 中存在该岗位关联 → 拒绝删除，报错提示"该岗位已关联 N 名员工，请先解绑"；无关联 → 软删除（GORM `DeletedAt`）；
3. **停用语义**：status=2 的岗位——① 不出现在 `getPostListAll`（员工侧下拉/选择器）；② 已有员工关联**保留不自动解绑**；③ 前端「分配员工」入口禁用（tooltip"岗位已停用"）；④ 治理列表仍可见、可筛选、可重新启用；
4. **双向绑定对称**：`setPostUsers(postId, userIds)` 与 `setUserPosts(userId, postIds)` 是同一张关联表的两个方向入口，均为全量覆盖、事务内 diff；一侧绑定后另一侧查询立即可见；
5. **员工删除清理**：删除用户（`DeleteUser`）事务内同步删除其 `sys_user_post` 行（对既有用户 service 的唯一侵入点）；
6. **无权限联动**：岗位不参与 casbin、菜单、数据权限的任何判定，纯业务标签；
7. **分页协议**：分页接口走 `request.PageInfo`（注意 `Paginate()` 将 pageSize 上限截为 100，见 §4.3）；全量接口（岗位下拉、岗位已关联员工回显）**不走** `Paginate()`，独立非分页查询——岗位数量与单岗位员工数均在几百人量级，无性能风险。

## 三、数据库设计

### 3.1 迁移文件

```
server/migrations/
├── 000011_create_sys_post.up.sql     # sys_posts + sys_user_post 两表 + 索引 + COMMENT + 岗位类型字典种子
└── 000011_create_sys_post.down.sql
```

> 迁移版本号分配前已核对 `server/migrations/`：当前最大版本为 000010（报表平台），本模块取 **000011**。
> 表结构同时注册进 `server/initialize/gorm.go` 的 AutoMigrate 列表（开发态 auto-migrate 生效、迁移负责版本化 DDL，与本仓库 report/ontology 模块双轨方式一致）。

### 3.2 建表 DDL（up.sql）

```sql
-- ============================================================
-- 1. sys_posts 岗位表（参考 JeeSite js_sys_post）
-- ============================================================
CREATE TABLE IF NOT EXISTS sys_posts (
    id          bigserial     PRIMARY KEY,
    created_at  timestamptz   NOT NULL DEFAULT now(),
    updated_at  timestamptz   NOT NULL DEFAULT now(),
    deleted_at  timestamptz,
    post_code   varchar(64)   NOT NULL,
    post_name   varchar(64)   NOT NULL,
    post_type   varchar(32)   NOT NULL DEFAULT '',
    sort        int           NOT NULL DEFAULT 0,
    status      smallint      NOT NULL DEFAULT 1,
    remarks     varchar(255)  NOT NULL DEFAULT ''
);
COMMENT ON TABLE sys_posts IS '岗位表（参考 JeeSite js_sys_post，独立模块，不涉数据权限）';
COMMENT ON COLUMN sys_posts.post_code IS '岗位编码（全局唯一，如 PM/HR）';
COMMENT ON COLUMN sys_posts.post_name IS '岗位名称（如 项目经理）';
COMMENT ON COLUMN sys_posts.post_type IS '岗位类型（字典 post_type 的 value）';
COMMENT ON COLUMN sys_posts.sort IS '排序（越小越靠前）';
COMMENT ON COLUMN sys_posts.status IS '状态 1启用 2停用';
CREATE UNIQUE INDEX IF NOT EXISTS uk_sys_posts_code ON sys_posts (post_code);
CREATE INDEX IF NOT EXISTS idx_sys_posts_type ON sys_posts (post_type);
CREATE INDEX IF NOT EXISTS idx_sys_posts_deleted_at ON sys_posts (deleted_at);

-- ============================================================
-- 2. sys_user_post 员工-岗位关联表（参考 JeeSite js_user_post，改 ID 关联）
-- ============================================================
CREATE TABLE IF NOT EXISTS sys_user_post (
    user_id     bigint   NOT NULL,
    post_id     bigint   NOT NULL,
    PRIMARY KEY (user_id, post_id)
);
COMMENT ON TABLE sys_user_post IS '员工-岗位关联表（N:N 双向绑定，硬删，无软删除）';
CREATE INDEX IF NOT EXISTS idx_sys_user_post_post ON sys_user_post (post_id);
```

**down.sql**：按 `DROP TABLE IF EXISTS sys_user_post; DROP TABLE IF EXISTS sys_posts;` 逆序删除；字典种子不回滚（字典属运营数据，down 仅删类型行可选）。

**要点**：

1. 关联表**复合主键 + 硬删除**：关联是纯关系数据，无审计诉求（操作留痕由写路由的 `OperationRecord` 中间件覆盖），不继承 `GVA_MODEL`；
2. `idx_sys_user_post_post` 支撑"岗位侧查员工"（复合主键已覆盖"员工侧查岗位"）；
3. `post_code` 唯一索引为**全局唯一**（不含 `WHERE deleted_at IS NULL`），与 `sys_departments.code` 的 gorm `uniqueIndex` 同式；因删除被 §2.2 规则 2 严格限制，编码释放场景极少（trade-off 见 §10）。

### 3.3 模型定义（范式）

```go
// server/model/system/sys_post.go
package system

import (
	"github.com/flipped-aurora/gin-vue-admin/server/global"
)

// SysPost 岗位表（参考 JeeSite js_sys_post；独立模块，不涉数据权限）
type SysPost struct {
	global.GVA_MODEL
	PostCode string `json:"postCode" form:"postCode" gorm:"column:post_code;size:64;not null;uniqueIndex;comment:岗位编码;" binding:"required"`
	PostName string `json:"postName" form:"postName" gorm:"column:post_name;size:64;not null;comment:岗位名称;" binding:"required"`
	PostType string `json:"postType" form:"postType" gorm:"column:post_type;size:32;default:'';comment:岗位类型 字典post_type;" binding:"required"`
	Sort     int    `json:"sort" form:"sort" gorm:"column:sort;default:0;comment:排序;"`
	Status   int    `json:"status" form:"status" gorm:"column:status;default:1;comment:状态 1启用 2停用;"`
	Remarks  string `json:"remarks" form:"remarks" gorm:"column:remarks;size:255;comment:备注;"`
	// 非持久化：岗位关联员工数（列表列）、岗位关联员工（详情）
	UserCount int64       `json:"userCount" gorm:"-"`
	Users     []SysUser   `json:"users" gorm:"many2many:sys_user_post;foreignKey:ID;references:ID;joinForeignKey:UserId;joinReferences:PostId"`
}

func (SysPost) TableName() string { return "sys_posts" }

// SysUserPost 员工-岗位关联（复合主键，硬删除）
type SysUserPost struct {
	UserId uint `json:"userId" gorm:"column:user_id;primaryKey;comment:用户ID;"`
	PostId uint `json:"postId" gorm:"column:post_id;primaryKey;comment:岗位ID;"`
}

func (SysUserPost) TableName() string { return "sys_user_post" }
```

> `Users` 的 many2many 标签仅用于 GVA_DB AutoMigrate 建表口径一致与可能的 Preload 场景；绑定/解绑一律通过显式操作 `SysUserPost` 完成（可控行数 diff，不走自动迁移隐式行为）。

### 3.5 字典种子（up.sql 内幂等插入）

岗位类型字典 `post_type` 随迁移种子分发（与迁移同事务语义；`post_seed.go` 中亦可兜底，见 §6.4）：

```sql
INSERT INTO sys_dictionaries (name, type, status, "desc", created_at, updated_at)
SELECT '岗位类型', 'post_type', true, '岗位管理-岗位类型（参考 JeeSite sys_post_type）', now(), now()
WHERE NOT EXISTS (SELECT 1 FROM sys_dictionaries WHERE type = 'post_type');

INSERT INTO sys_dictionary_details (label, value, sort, status, sys_dictionary_id, created_at, updated_at)
SELECT v.label, v.value, v.sort, true, d.id, now(), now()
FROM sys_dictionaries d,
     (VALUES ('高层岗位', 'high', 1), ('中层岗位', 'middle', 2),
             ('基层岗位', 'primary', 3), ('普通岗位', 'common', 4)) AS v(label, value, sort)
WHERE d.type = 'post_type'
  AND NOT EXISTS (
    SELECT 1 FROM sys_dictionary_details x
    WHERE x.sys_dictionary_id = d.id AND x.value = v.value
  );
```

> 初始值仅是建议口径（对齐 JeeSite 岗位类型四分法），实施时或上线后可在「字典管理」自行增删改，不影响代码。明细表外键列名已按 baseline 核对：`sys_dictionary_details.sys_dictionary_id`。

### 4.2 API 清单（10 个，ApiGroup =「岗位管理」）

| # | 路由 | 方法 | 说明 | 请求 | 响应 |
|---|---|---|---|---|---|
| 1 | `/post/createPost` | POST | 创建岗位 | SysPost（body） | msg |
| 2 | `/post/updatePost` | PUT | 更新岗位 | SysPost（body，含 ID） | msg |
| 3 | `/post/deletePost` | DELETE | 删除岗位（有关联拒绝） | `?ID=` | msg |
| 4 | `/post/findPost` | GET | 岗位详情 | `?ID=` | SysPost |
| 5 | `/post/getPostList` | POST | 分页列表（含 userCount 列） | SysPostSearch（body） | PageResult{list, total} |
| 6 | `/post/getPostListAll` | GET | 全部**启用**岗位（下拉/多选，不分页） | 无 | `{list: []SysPost}` |
| 7 | `/post/getPostUsers` | GET | 岗位已关联员工全量（回显/详情） | `?postId=` | `{list: []UserBrief}` |
| 8 | `/post/setPostUsers` | POST | 岗位绑定员工（全量覆盖） | SetPostUsersReq | msg |
| 9 | `/post/getUserPosts` | GET | 员工已关联岗位（回显） | `?userId=` | `{list: []SysPost}` |
| 10 | `/post/setUserPosts` | POST | 员工绑定岗位（全量覆盖） | SetUserPostsReq | msg |

`UserBrief`：`{ID, userName, nickName, departmentId, departmentName}`——只取绑定弹窗与回显所需列，不吐手机号/邮箱等敏感字段。

handler 范式完全对齐 `sys_department.go`：`ShouldBindJSON/ShouldBindQuery` → `postService.Xxx()` → `response.OkWithMessage/OkWithDetailed/FailWithMessage`，错误统一 `global.GVA_LOG.Error + zap`。

### 4.3 关键 Service 逻辑

```go
// server/service/system/sys_post.go（范式示例）
package system

// CreatePost：编码唯一校验（含软删行，全局唯一）→ Create
func (postService *PostService) CreatePost(post *system.SysPost) error {
	var count int64
	global.GVA_DB.Model(&system.SysPost{}).Where("post_code = ?", post.PostCode).Count(&count)
	if count > 0 {
		return errors.New("岗位编码已存在")
	}
	return global.GVA_DB.Create(post).Error
}

// DeletePost：有关联员工禁止删除
func (postService *PostService) DeletePost(id uint) error {
	return global.GVA_DB.Transaction(func(tx *gorm.DB) error {
		var count int64
		tx.Model(&system.SysUserPost{}).Where("post_id = ?", id).Count(&count)
		if count > 0 {
			return fmt.Errorf("该岗位已关联 %d 名员工，请先解绑后再删除", count)
		}
		return tx.Delete(&system.SysPost{}, "id = ?", id).Error
	})
}

// SetPostUsers：全量覆盖（diff），事务内
func (postService *PostService) SetPostUsers(postId uint, userIds []uint) error {
	return global.GVA_DB.Transaction(func(tx *gorm.DB) error {
		// 1. 岗位存在性校验（软删/不存在报错；停用不拦截——解绑场景仍需可用，
		//    停用岗位的"绑定"入口由前端禁用，后端仅校验存在性）
		// 2. 查现有关联 postId 的 userId 集合 oldSet
		// 3. newSet = userIds 去重
		//    remove = oldSet - newSet → 硬删 Delete(&SysUserPost{}, "post_id = ? AND user_id IN ?")
		//    add    = newSet - oldSet → 批量 Insert；插入前校验 userIds 均存在且未软删
		// 4. 无变更则直接返回 nil
		return nil
	})
}

// SetUserPosts：与 SetPostUsers 对称，主键方向换为 user_id / post_ids

// GetPostList：分页 + keyword(code/name like) + postType + status，
// userCount 用子查询一次性带回：
//   SELECT p.*, (SELECT count(*) FROM sys_user_post up WHERE up.post_id = p.id) AS user_count FROM sys_posts p ...
//   （gorm 实现：Model(&SysPost{}) + Select 子查询 + PageInfo.Paginate() + Count 分离）

// GetPostListAll：非分页——不使用 PageInfo.Paginate()（其将 pageSize 截为 ≤100），
// 直接 Where("status = 1").Order("sort, id").Find，返回全部启用岗位

// GetPostUsers：非分页，联 sys_users（未软删）取 UserBrief 列
// GetUserPosts：非分页，联 sys_posts（未软删，含停用——员工已挂的停用岗位要如实回显）
```

**分页协议注意**：`request.PageInfo.Paginate()`（`server/model/common/request/common.go`）会把 `pageSize > 100` 截断为 100、`<= 0` 兜底为 10。因此"全量"诉求（§2.2 规则 7）一律走独立非分页接口（6/7/9 号），**不要**试图用 `pageSize: 9999` 穿透分页接口。

### 4.4 与用户模块的边界

- **不改** `CreateUser`（`admin_register`）与 `SetUserInfo` 的签名与逻辑——员工侧绑定通过 10 号接口在保存成功后由前端串行调用（§5.4）；
- **仅改** `DeleteUser`：事务内追加 `tx.Where("user_id = ?", id).Delete(&system.SysUserPost{})`，防悬空关联；
- 用户模块现有 `GetUserInfoList`（含 departmentId 子树过滤）被 8 号接口的前端弹窗复用，不做修改。

**交互与数据流**：

1. **打开时**：`getPostUsers(postId)` 拉全部已关联员工 → `selectedMap`（ID → UserBrief）；列表中已选行回显勾选（`toggleRowSelection`）；
2. **部门过滤**：左树 `getDepartmentList()`（现有接口，返回树）；选中任意层级节点 → 以该节点为 `departmentId` 调 `getUserList`（后端 `GetUserInfoList` 已实现含子部门过滤：`GetDepartmentSubTreeIds`），`check-strictly` 使任意层级可选；"全部部门"= 不传；

4. **勾选**：分页翻页不丢已选——勾选/取消即时同步 `selectedMap`；跨页已选统一在"已选"标签区展示、可单独 × 移除（移除后若该行在当前页，同步取消勾选）；
5. **保存**：`setPostUsers(postId, Object.keys(selectedMap))` 全量覆盖 → 成功后刷新列表（userCount 变化）；
6. 翻页数据源固定为 `/user/getUserList`（请求字段 `page/pageSize/nickName/username/departmentId`；该接口自行 limit/offset，无 `Paginate()` 的 100 上限，弹窗内固定 pageSize 20）。

## 十、风险与注意事项

1. **员工侧两段保存非原子**：用户保存成功但 `setUserPosts` 失败时出现"用户已建、岗位未挂"。缓解：失败 toast 明确提示重试路径；用户行内可再次进入编辑补挂。若未来要求强一致，可改为把 postIds 揉进用户保存事务（需动用户 API 签名，本期裁定不做，见 §1.3-4）；
2. **并发全量覆盖后写胜出**：两个管理员同时分配同一岗位/员工时后者覆盖前者。量级与场景下风险可接受，操作留痕（OperationRecord）可追溯；
3. **软删后编码不可复用**：`post_code` 全局唯一索引（与 department 同式）。岗位删除本就受"有关联禁删"限制，实际影响极小；若未来需要编码复用，改为 PG 部分索引 `WHERE deleted_at IS NULL` 并同步 gorm 标签（ontology 域既有实践）；
4. **`Paginate()` 的 pageSize 上限 100**：一切"全量"场景必须走 6/7/9 号非分页接口，勿用大 pageSize 穿透（§4.3）；
5. **字典被运维删除**：`post_type` 字典行若被删，岗位类型下拉为空、列表类型列显示裸 value。表单 required 校验可拦截新建，存量数据不受影响；字典管理可随时重建；
6. **菜单锚定降级**：种子以 `name='department'` 定位「超级管理员」目录，若现场环境该菜单 name 被改过则降级为顶级菜单，需人工挪动一次（种子只保证不失败，不保证位置完美）；
7. **many2many 标签与显式操作并存**：`SysPost.Users` 的 many2many 标签仅服务 AutoMigrate 建表口径，业务读写一律显式操作 `SysUserPost`，避免 GORM 关联自动行为的隐式删除/插入（§3.3 注）；
8. **分配员工弹窗的数据权限边界**：弹窗复用 `getUserList`，自带 DataScope 过滤（§5.3 注记）——岗位管理若下放给数据范围受限角色，可选员工集合随之收缩；本期仅授 888，无影响。
